## 构建机上的补充验证（2026-11-25）

在构建机（macOS 27.2.0、arm64）用 `kcode-main` 源码构建的 Helper（build `0d73de679e4e637b2477`、IPC v3）补做工程层与真机验证。这些结果说明代码在真实 AX、ScreenCaptureKit 与事件派发下的行为，不是 M02–M11 的验收证据。

- **工程层新增回归**，都先确认在修复前失败：
  - 元素重定位：窗口节点数超过遍历上限时，截断点之后还有同角色、同标识的控件。原先返回先找到的那个，现在按 `element_unavailable` / `not_sent` 拒绝；唯一匹配、完整搜索到两个匹配两种结果不变。
  - 跨进程 lease 竞争：五个独立进程争同一个 runtime 目录。活着的对手被拒，对手正常退出后才能取得；持有者被强杀后 lease 文件保留、状态如实报告，可以回收；两台同时起步只有一个赢家。夹具首先暴露一条缺口：被拒的写操作没有 `dispatch_status=not_sent`，现已在 lease 获取处统一补上。
- **真机链路**：Helper 作为脚本子进程直接启动，继承宿主应用的辅助功能与录屏授权。这只用于验证输入与截图代码，不代表 Helper 自身的授权状态，也没有改动任何 TCC 记录。
  - 工具连接上 `pip_is_running` 可读，`pip_start`、`pip_stop`、`pip_clear_dismissed`、`pip_session_event` 均为 `not_authorized`；Node 以 presentation 角色握手被拒。
  - 新鲜采样：常驻进程报 `granted`，同一 bundle 经 LaunchServices 起的短命进程报 `denied`，`request_access` 以新鲜结果返回 `ready=false`。
  - 观察与 AX：取得 700 × 612 px、非空白的原生帧，随帧带进程出生身份与显示拓扑指纹；`set_value` 与按复选框经夹具回环接口核对生效。
  - 两台真实 Helper：B 的只读观察可用，写操作被拒 `controller_busy`，回执 `not_sent` 并附 A 的 PID；A 停止控制后 B 的写入生效。
- **桌面 E2E**：`computer-use-permission-status` 在构建机本机通过（2 个用例，首次通过率 100%）。本机运行需要清掉从已安装应用继承的 `ZCODE_*` 环境变量，并指定 `E2E_PROVIDER_REPLAY_FIXTURE_PATH`；运行后开发版 Electron 会成为 `zcode://` 的默认处理器，需要恢复。
- **打包**：本地未签名包内的 Helper 与源码 build 一致，`CFBundleURLTypes` 声明了 `zcode`。`doctor:macos-release` 对未签名包按设计在 `codesign --verify --deep --strict` 处失败，与同日已安装的包结果一致。
- **未成立或未验证**：
  - 产品启动路径（LaunchServices）下，本机没有给 KCode 的 Helper 授权，两项权限都是 `denied`。
  - 事件送达但控件不动作：`type` / `paste` 的 ⌘V、坐标点击的按下与抬起都到达目标窗口，控件状态没有变化。基线构建 `fa4fbb7305aea3533273` 结果相同；不经 Helper、直接向夹具进程投递 ⌘A 也同样不生效。是否影响 Chrome 等真实应用需在 M07 / M08 确认。
  - PiP 面板与 ghost cursor 需要签名 Host 的 presentation 连接，本机的 ad-hoc 包没有这条链路。
  - 系统设置里真实撤销录屏授权后的采样没有做，它需要重置本机的授权。
  - 真实 OAuth 回调没有做：需要真实登录，并且会改动本机 `zcode://` 的默认处理器。
  - 设置页在“已授权但锁屏”时仍只显示两项已授权，没有锁屏提示（规范 §8.1）。E2E 现在可以在本机运行，这项可以按“先维护 E2E、再改交互与文案”推进。

## 真机复验：后台输入的落地核对与观察（2026-11-26）

用上一节的签名 Release（Helper build `9dc2116fe31aa431b872`）在构建机上经产品链路复验：隔离的 Chrome 158 与 AppKit 夹具都不在前台，窗口被完全遮挡。文字全部进了目标控件（页面事件逐字记到），但落地核对通过并不是因为看到了首字。三处问题同源，一并修复。

### 复验发现

1. **输入框的值不随按键更新。** 每次操作结束后读到的多行框的值都等于输入之前的内容；再按 4 个键，1–2 秒内读到的仍是旧值，给控件设辅助功能焦点才变。上一节写的“单个按键后立即更新、连发后要等下一次按键补齐”是错的：当时每次读数前都重新设过焦点。
2. **焦点元素的报告同样滞后。** 给控件设辅助功能焦点之后，应用级焦点元素在几毫秒到上百毫秒内仍是上一个控件。实测给只读的多行框输入 `hello`：基线取自上一个控件（空串），首字之后焦点报告换成只读框，核对看到“值变了”就放行，5 个字符全部发出，回执 `accepted`，值其实没变。同一个控件换成中文首字则正确中止——结果取决于时间窗。
3. **输入之后再观察，读到的是输入之前的值。** 早上首轮复验里“多行框换行”一条脚本读到的落地内容为空，就是它。对真实模型来说，`type` 成功后下一次观察看不到输入的文字，会误判失败。

原因在 Chromium 源码里对得上（`third_party/blink/renderer/modules/accessibility/ax_object_cache_impl.cc`、`core/frame/local_frame_view.cc`）：辅助功能树的序列化挂在渲染帧上（`ScheduleAXUpdate` 只在未被节流的 frame view 上请求视觉更新），被完全遮挡的页面不跑帧；只有辅助功能动作触发的事件（`EventFrom::kAction`）会立即序列化，`RunAccessibilitySteps` 也只处理未节流的 frame view。按键不是动作。

### 修复

- **读值之前先请应用发出待发的更新**：对应用元素在落点控件中心做一次命中测试（只读的 `AXUIElementCopyElementAtPosition`）。严格对照 7 次，请求后 12–17 毫秒辅助功能值与页面完全一致，光标不动。只读值、读选区、读位置、对控件自身做命中测试都不触发。另外两个会刷新的候选不采用：再设一次焦点有一次没有刷新；把读到的选区原样写回去，写回的是过期位置，光标被挪到了旧位置。基线等到值不再因这次请求变化；首字之后在落地时限内重复请求。
- **基线读自真正接收输入的控件**：带定位元素时（`focus_native`、`click_native`）直接读定位的元素；没有定位元素时记下读基线的元素，核对途中焦点元素变了就以它重新取基线，下一个带字符的按键再核对。最坏多发出一个未经核对的字符。
- **首字之后读不到值不算落地**（原先读不到也算通过）。
- **观察遍历读到网页内容的根（`AXWebArea`）时先做一次命中测试**，稍等再读它的子节点；没有网页内容的窗口不做。
- 等待循环改成真正的休眠：worker 线程的 run loop 没有源，`CFRunLoopRunInMode` 立刻返回，原先 400 毫秒的落地时限里读了几千次辅助功能。

规范 §9.1、§9.3 同步更新。

### 回归

- `text-background-native.mm` 改为把“应用里的真实值”和“辅助功能读到的值”分开建模，覆盖：值要等应用发出更新才读得到、输入框不接收按键、首字之后读不到值、带定位元素而焦点报告滞后、没有定位元素而焦点报告在核对途中变化、窗口树查找、中途取消、各类拒绝、前台仍走粘贴。对已提交的实现（`e93d9547`）失败在“值要等应用发出更新”（首字进了输入框，实现却报 `foreground_required`）；对只修第一处的中间版本失败在“带定位元素而焦点报告滞后”（只读框回执成了 `accepted`，即上面的发现 2）。
- 新增 `observe-web-native.mm`：观察网页内容时做一次命中测试并读到更新后的值，没有网页内容的窗口不做。对已提交的 `observation.mm` 失败在第一条断言（没有命中测试）。

### 已知边界

- **窗口全程被遮挡时新加载的文档不发初始树。** 实测在后台把隔离 Chrome 导航到新页面后，网页内容的辅助功能树消失，观察不到网页内容，`type` 无法按元素定位；按“返回”重新加载后树才出现。M2 上也复现：后台启动的隔离 Chrome 打开 `type2.html`，模型第一次观察只有 37 个元素（浏览器外壳），找不到输入框。这是 Chromium 的行为（初始树也靠渲染帧发出），没有绕过办法；窗口露出一次（哪怕一两秒）即可恢复，M2 上短暂置前后树出现，六条场景随之全部可执行。
- **读不到落点时不核对，回执只证明派发。** 实测向不可编辑的 AppKit 文本框（`NSTextField`，`editable = NO`）输入 `hello`：焦点落在窗口上，没有值为字符串的焦点元素，5 个按键全部发出，回执 `accepted`，值不变。与规范一致（找不到落点就只报告派发），但模型必须按规范在动作之后观察真实效果。
- 没有定位元素、焦点报告又在基线之后才更新时，最坏多发出一个未经核对的字符（规范 §9.3）。
- **Chrome 157 在后台丢弃代理对按键。** M2 的 Chrome 157.0.8103.80：后台 `type` 里 emoji（代理对整对发出的按键）不进输入框，页面 DOM 里也没有（镜像行确认真值），回执 `accepted`（只证明派发）；B、G 两条场景两次复现。同一构建机的 Chrome 158 后台可以输入（与页面逐字符对照 7/7）。AppKit 不受版本影响（M2 原生夹具里 😀 正常落地）。差异在 Chromium 对多单元按键的输入法提交路径，157 与 158 行为不同；没有不改应用版本就能绕过的派发方式，模型观察会发现字符缺失并改用 `set_value`。
- **被完全遮挡的窗口，截图是旧帧。** M2 的镜像检查任务里，模型两次截图都看到输入框为空，而 AX（读 DOM）里值都在——页面不重绘，窗口表面停留在输入之前的画面。模型据此得出「AX 是过期缓存、像素才是真值」的反向结论，从它掌握的证据看是合理的。后台场景里 DOM（AX）是最新的真值，像素和页面自身的事件都可能滞后。
